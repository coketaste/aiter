What is AITER?

AITER is a unified collection of production-ready GPU operators (attention, MoE, GEMM, normalization, quantization, communication) that framework developers integrate directly into their inference/training stacks. It is the default kernel backend for LLM inference on AMD GPUs, powering vLLM, SGLang, ATOM and JAX on ROCm.

Core design principles

Dual-level API

Every operator is callable from both Python (PyTorch tensors) and C++. Python is the primary integration surface.

Multi-backend

Each op may have several implementations — Triton CK ASM Opus — selected at runtime by shape/hardware.

JIT-first

C++/HIP kernels are compiled on demand on first call and cached, keeping the install lightweight. An AOT path exists for prebuilt deployments.

Autotuned

Per-shape best configs ship as CSV files in aiter/configs/ and are looked up at runtime to pick the fastest kernel instance.

Architecture

AITER is a layered stack: a stable Python/C++ API on top, a JIT compilation engine in the middle, and four interchangeable kernel backends at the bottom.

The layer stack

1
Public APIaiter/__init__.py re-exports every operator into the flat aiter.* namespace (e.g. aiter.gemm_a8w8, aiter.flash_attn_func).
2
Operator wrappersaiter/ops/*.py + high-level orchestrators like aiter/fused_moe.py, aiter/mla.py. Pick backend, prep tensors, dispatch.
3
JIT engineaiter/jit/core.py — the @compile_ops decorator builds & loads the right native module on first call, then caches it.
4
Binding layercsrc/pybind/*_pybind.cu (pybind11) and csrc/cpp_itfs/ (ctypes/AOT interfaces) expose native functions to Python.
5
Kernel backendsTriton JIT • Composable Kernel (CK) templates • hand-tuned ASM .co • Opus HIP kernels — the actual GPU compute.

Two execution modes

JIT (default)

On import aiter, only Python loads. A native module compiles the first time an op needing it is called, then is cached on disk & in-process. Lightweight install, slower first call.

AOT

aiter/aot/ + AITER_AOT_IMPORT=1. Kernels are prebuilt at install time for fast, reproducible cold-start in production/containers.

Triton-only mode (AITER_TRITON_ONLY=1, always on Windows): exposes only Triton ops and skips all CK/HIP JIT — useful when there's no C++ toolchain.

JIT Build System

The heart of AITER. aiter/jit/core.py turns a bare Python function stub into a compiled, cached, type-checked native operator — transparently.

The @compile_ops contract

An op module declares a stub with no body. The decorator owns everything: locating build args, compiling on cache-miss, loading the module, and binding the real native function over the stub.

# aiter/ops/gemm_op_a8w8.py
@compile_ops("module_gemm_a8w8", fc_name="gemm_a8w8", gen_fake=gen_gemm_a8w8_ck_fake_tensors)
def gemm_a8w8_ck(XQ, WQ, x_scale, w_scale, Out, bias=None, splitK=0) -> Tensor: ...
                                              # ↑ empty body — filled in by JIT

Decorator parameters

ParamMeaning
_md_nameNative module name to build/load (e.g. module_gemm_a8w8)
fc_nameSymbol to fetch from the built module (defaults to the Python fn name)
gen_funcOptional: compute per-call build args (for shape-specialized builds)
gen_fakeFake/meta-tensor impl so the op composes with torch.compile
ffi_type"pybind" (default) or "ctypes" binding style

Build args per module are declared in aiter/jit/optCompilerConfig.json and resolved by get_args_of_build — sources, extra include dirs, cc/hip flags, codegen ("blob gen") commands, and link flags.

Runtime safety & ergonomics

  • Auto signature/type-check — on first bind the decorator parses the pybind docstring to reconstruct a Python signature and validate tensor args.
  • torch.compile guard — torch_compile_guard + gen_fake let JIT ops trace cleanly under Dynamo without recompiling kernels.
  • Multiprocess-safe — FileBaton locks serialize the first build across ranks; late processes wait then load.
  • Rebuild hook — AITER_REBUILD=1 forces a one-time recompile of each touched module.

Kernel Backends

One operator, many implementations. AITER's value is curating the fastest kernel per shape/arch across four very different technologies.

Triton  Portable Python-authored kernels

Located under aiter/ops/triton/ (319 files). Organized by domain: attention/, gemm/, moe/, normalization/, quant/, rope/, comms/, plus _triton_kernels/ and gluon/ (Gluon-dialect kernels). Compiled by Triton's own JIT at runtime; no hipcc needed. This is the only backend in Triton-only / Windows mode.

CK  Composable Kernel templates

Each csrc/ck_*/ directory is a family of templated C++ kernel instances (e.g. ck_gemm_a8w8/, ck_gemm_a4w4_blockscale/, ck_batched_gemm_bf16/, ck_tile_gemm_moe_2stages/). A codegen step ("blob gen") emits the specific instances needed, then hipcc builds them via the JIT. CK depends on the pinned Composable Kernel submodule, cloned on demand.

ASM  Hand-tuned code objects

The hsa/ tree holds 2810 prebuilt .co AMDGPU code-object binaries, partitioned by architecture: hsa/gfx942/ (CDNA3), hsa/gfx950/ (CDNA4), hsa/gfx1250/. Categories include fmha_v3_fwd/bwd (attention), fmoe* (fused MoE), bf16gemm/, f4gemm/, and fused all-reduce+norm. They're launched from csrc/py_itfs_cu/asm_*.cu wrappers and the csrc/cpp_itfs/hsaco_launcher.py. CSV manifests (e.g. fmha_bwd_dqdkdv.csv) map shapes → the right .co.

Opus  Lightweight HIP DSL

A single-header C++ template library (csrc/include/opus/opus.hpp) for authoring new HIP kernels with vectorized load/store, MFMA wrappers and layout helpers — positioned above raw HIP but below CK/CUTLASS in complexity, with a strong focus on fast compile times. Used by newer ops (moe_sorting_opus, pa_sparse_prefill_opus) and csrc/opus_gemm/. See the Opus & Dev tab.

A single high-level op like Fused MoE (aiter/fused_moe.py) can dispatch to ASM, CK, Opus or FlyDSL kernels depending on dtype (A8W8/A4W4/MXFP4), shape and env flags — defaulting to Opus MoE sorting unless AITER_USE_CK_MOE_SORTING=1.

Op Call Flow — End to End

Tracing one quantized GEMM call from Python down to a GPU kernel.

The journey of aiter.gemm_a8w8(...)

1
User codeCalls aiter.gemm_a8w8(XQ, WQ, x_scale, w_scale) — exported from aiter/ops/gemm_op_a8w8.py.
2
Wrapper picks an instanceThe high-level wrapper consults the tuned CSV (a8w8_tuned_gemm.csv) for this (M,N,K) to choose CK vs ASM vs splitK, pads M, allocates Out.
3
@compile_ops stubCalls gemm_a8w8_ck(...). Decorator checks the module cache for module_gemm_a8w8.
4
JIT build (first time only)build_module reads optCompilerConfig.json, runs blob-gen to emit CK instances, compiles with hipcc → .so. Subsequent calls skip straight to load.
5
pybind bridgecsrc/pybind/gemm_a8w8_pybind.cu exposes gemm_a8w8; decorator does getattr(module, "gemm_a8w8").
6
GPU kernel runsThe CK (or ASM) kernel executes on the AMD GPU; result written into Out and returned as a torch tensor.

How an op file is structured

# aiter/ops/gemm_op_a8w8.py — the recurring pattern
def gen_..._fake_tensors(...):  # meta impl for torch.compile
    return Out

@compile_ops("module_gemm_a8w8", fc_name="gemm_a8w8", gen_fake=...)
def gemm_a8w8_ck(...) -> Tensor: ...    # native stub

# a public Python orchestrator selects instance from tuned CSV,
# then calls the stub(s). Exported via aiter/__init__.py
The same three-part shape — fake-tensor fn → @compile_ops stub → orchestrator — recurs across nearly all 43 op modules in aiter/ops/. Learn it once and every operator reads the same way.

AITER ships pre-measured "best kernel per shape" tables so production picks the fastest instance with zero runtime search.

tuned vs untuned

*_tuned_*.csv

The authoritative lookup used at runtime: each row maps a problem shape to the winning kernel/config. Curated & checked in.

*_untuned_*.csv

Candidate shape lists fed to the offline autotuning pipeline, which benchmarks them and emits the tuned table. See docs/autotuning_pipeline.md.

Set AITER_LOG_TUNED_CONFIG=1 to log which tuned entry was chosen for a given call — invaluable when debugging a "why is this shape slow?" question.

Opus & Kernel Development

Opus is AITER's in-house DSL for authoring HIP kernels quickly — with a defining obsession on compile-time.

What Opus is

opus = "AI operator microu std". A single header, csrc/include/opus/opus.hpp, inspired by ck_tile and CUTLASS/cute but deliberately minimal. Just #include "opus/opus.hpp" — no separate build step.

What it gives you

  • AMDGPU data-type declaration & conversion
  • Automated vectorized buffer load/store dispatch
  • MFMA matrix-core wrappers (swap MFMA types with minimal edits)
  • Device-side utility functions
  • Optional lightweight layout abstractions for index math

What it deliberately is NOT

  • No prebuilt GEMM/attention kernels (use CK or AITER)
  • No reusable device pipelines
  • No unified tensor class — providers & layouts kept separate
  • Not a full arbitrary-transform layout system

Positioning: above hand-written HIP, below ck/CUTLASS. Claimed up to 61× faster builds than a standard torch extension build.

Two skills assist Opus work: opus-kernel-best-practice (compile-time optimization for individual kernels) and opus-module-build-optimization (module-level first-call build-wall tuning). Examples live in op_tests/opus/.

Adding a new native operator (the pattern)

1
Write the kernelAdd HIP/CK/Opus source under csrc/ (e.g. kernels/ or opus_gemm/).
2
Expose via pybindAdd a *_pybind.cu in csrc/pybind/ binding your function name.
3
Register build argsAdd a module entry to aiter/jit/optCompilerConfig.json (sources, flags, includes).
4
Declare the Python stubNew file in aiter/ops/: a gen_fake, an @compile_ops(...) stub, optional orchestrator. Export from __init__.py.
5
Add a testCreate op_tests/test_yourop.py validating against a torch reference.

See CONTRIBUTE.md and docs/isa_kernel_optimization.md for full conventions.

Getting Started

Install

# clone with submodules (CK lives in 3rdparty/)
git clone --recursive https://github.com/ROCm/aiter.git
cd aiter
python3 setup.py develop      # installs triton automatically

Forgot --recursive? Run git submodule sync && git submodule update --init --recursive.
